# Описание продукта (для кабинета)

<!-- markdownlint-disable MD013 -->

**Название:** Цифровой механик — агентный помощник механика по акустическим проверкам двигателей.

**Задача хакатона:** автоматизировать разбор результатов акустической диагностики, поиск в руководствах по ремонту конкретного двигателя и подготовку заявки в ТОиР с подтверждением человеком.

## Что делает продукт

1. Получает результат ML-проверки (код неисправности, уверенность, признаки) и карточку машины.
2. Многошаговый агент (инструменты, журнал шагов): поиск по индексу руководств **этого** двигателя, чтение страниц PDF, подбор **названий деталей**, формирование **явного** черновика заявки.
3. Ответ механику обычным текстом (без Markdown/JSON): признаки, риск, **короткие** цитаты со ссылкой «документ, стр. N», пошаговый ремонт.
4. В интерфейсе: краткое превью нужной страницы PDF (без публикации полных руководств в Git), режимы процедуры «полный / профи», блок запчастей с выбором деталей, блок «Заявка в ТОиР», карточка машины (история, преемственность ремонта, токены).
5. Заявку в ТОиР отправляет **только механик** после явного подтверждения (приоритет можно изменить).

## Возможности агента (актуально)

| Возможность | Как проявляется |
| --- | --- |
| Агентный цикл | Инструменты: `get_vehicle`, `list_checks`, `get_check`, `explain_code`, `search_manual`, `read_pages`, `search_spare_parts`, `ticket_history`, `draft_ticket`. Отправки в ТОиР в TOOLS нет. |
| Только свой двигатель | RAG и ссылки в заявке отфильтрованы по двигателю машины; чужие руководства (например 536.* для ЯМЗ-236) не используются. |
| Сбой записи / норма | Без LLM-диагноза и без заявки при `check_failed` / `bad`; при `normal` — краткий ответ без ремонта. |
| Цитаты и страницы | Дословные фрагменты со страниц PDF; оглавление запрещено; в UI — PNG страниц процедуры. |
| Резервный черновик | Если модель не собрала `draft_ticket`, код собирает явный черновик по страницам процедуры (механика может подтвердить). |
| Запчасти | Кандидаты-детали для выбора (без привязки к магазину и производителю; демо-поиск по поломке). В заявку попадают только названия деталей, не шаги ремонта. |
| Приоритет | `high` / `medium` / `low` с обоснованием; пороги уверенности 0,50 (заявка) и 0,56 (не повышать срочность). |
| Противоречия РЭ/РК | Баннер для известных расхождений (ЯМЗ-236, зазоры клапанов). |
| Экономика | Учёт токенов и стоимости в журнале / карточке машины. |
| Голос | Озвучка шагов ремонта в UI (Web Speech, кодовое слово «Помощник»). |

## Технологии

| Компонент | Реализация |
| --- | --- |
| Backend | Python 3.12, FastAPI |
| LLM | YandexGPT (`LLM_PROVIDER=yandex`) на стенде |
| Поиск | Гибрид BM25 + BGE-M3 (RRF), CPU; опционально Tesseract OCR |
| Данные | PDF руководств, 50 машин, журнал SQLite |
| Интеграции | REST к ML и ТОиР (OpenAPI заказчика) |
| Деплой | Docker Compose, HTTPS |

Публичный репозиторий: `https://github.com/Edwards359/iikuznitsa-digital-mechanic`.  
Демо: `https://5.129.222.124:8080` (самоподписанный сертификат).

## Три сценария демо (заказчик)

1. **Отклонение** — риск, ссылки на страницы, черновик → подтверждение → `ticket_id`.
2. **Вопрос по руководству** — ответ с цитатой и номером страницы.
3. **Сбой записи** — без диагноза и без заявки.

Кратко: [docs/demo-scenarios.md](demo-scenarios.md).

## Экономика эксплуатации (ориентир)

- YandexGPT на стенде — порядка **1,2 ₽ / 1000 токенов** (см. `docs/cost-operation.md`).
- Embeddings и OCR локально (токены LLM не тратятся).
- Голос на демо: Web Speech, 0 ₽.

## Эффект

Меньше времени механика на поиск процедуры в PDF и оформление заявки; меньше риска сослаться на чужое руководство или подставить в заявку «процесс» вместо детали.

## Готовность

Рабочий прототип на данных задачи: гибридный поиск, агент, UI, логирование, деплой, выбор деталей в заявку, подтверждение человеком.
